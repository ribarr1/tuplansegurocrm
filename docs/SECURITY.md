# Seguridad

Notas de seguridad específicas del proyecto. No es una política general — solo decisiones concretas que no son obvias a partir del código.

## Autenticación

- **Librería:** [Better Auth](https://www.better-auth.com/), self-hosted, open source (MIT). Elegida sobre Auth.js/NextAuth porque soporta sesiones respaldadas por base de datos junto con el proveedor de email+password — Auth.js solo permite JWT con `CredentialsProvider`, lo cual no permite revocar acceso en tiempo real cuando `User.isActive` cambia. Ver [DECISIONS.md](./DECISIONS.md) para el análisis completo.
- **Password hashing:** scrypt (implementación interna de Better Auth sobre `node:crypto`, sin dependencias nativas). Nunca criptografía propia. El hash vive en `Account.password` — **nunca** en `User` ni en ningún log.
- **Longitud mínima de contraseña:** 10 caracteres (`emailAndPassword.minPasswordLength` en `src/lib/auth.ts`), reforzada también en el script de bootstrap.
- **Sesiones:** cookie `HttpOnly`, `Secure` en producción, `SameSite` por defecto de Better Auth. Nunca tokens de sesión en `localStorage`. Sesiones respaldadas por la tabla `session` (base de datos), no JWT-only.
- **Sin login social todavía** (Google/Facebook/Microsoft) — solo email + password. El modelo `Account` ya soporta múltiples proveedores si se agrega después, sin nueva migración estructural para eso.
- **Sin registro público — reforzado a nivel de Better Auth desde Fase 019.5.** No existe endpoint `/signup` ni flujo de alta abierto en la UI, y desde Fase 019.5 la ruta pública de Better Auth (`/api/auth/sign-up/email`) queda además **bloqueada incondicionalmente** vía `emailAndPassword.disableSignUp: true` (`src/lib/auth.ts`) — antes solo no se enlazaba desde ningún lado, pero seguía siendo alcanzable por cualquiera que conociera la ruta. El único mecanismo de creación de usuarios es `npm run create-admin` (bootstrap del primer ADMIN) y Configuración → Usuarios (ADMIN, ver sección "Administración de usuarios" abajo) — ambos emiten una invitación de un solo uso, nunca una contraseña definida por un tercero.
- **Bootstrap del primer ADMIN:** `scripts/create-admin.ts`. Solo puede ejecutarse cuando NO existe ningún `User` con `role=ADMIN` (verificado con una consulta explícita antes de crear nada) — una vez creado el primer ADMIN, el comando se niega a ejecutarse de nuevo, incluso con un correo distinto; administradores adicionales se crean desde Configuración → Usuarios (con auditoría de qué ADMIN los creó). Nunca recibe ni define una contraseña — construye `User`+`Account` (`password: null`) y emite una invitación de un solo uso (24h, hash SHA-256, ver "Invitación y activación de cuentas" abajo) igual que cualquier usuario nuevo creado desde la UI. Si `RESEND_API_KEY`/`EMAIL_FROM` están configurados, envía el enlace por correo; si no, lo imprime UNA vez en la terminal como último recurso (nunca en un archivo). Se audita (`ADMIN_BOOTSTRAP_CREATED`) sin exponer el token.
- **Contraseñas de usuarios locales de prueba deben rotarse después de las pruebas** (o el usuario debe eliminarse si solo era para verificación puntual). Ninguna credencial de prueba se versiona ni se documenta en texto plano en el repositorio — cuando aparece en esta documentación o en el chat de una fase, es exclusivamente para el entorno local del desarrollador, nunca para producción.
- **MFA — implementado (PREPRODUCCIÓN, MFA para ADMIN y operaciones financieras).** Ver sección dedicada "Autenticación en dos pasos (MFA)" más abajo.
- **Recuperación de contraseña por email — implementada (PREPRODUCCIÓN, Correos/invitaciones).** Usa el endpoint NATIVO de Better Auth (`emailAndPassword.sendResetPassword`/`/api/auth/request-password-reset`+`/reset-password`), envuelto por `src/services/password-recovery.service.ts` para agregar lo que Better Auth no cubre por sí solo: (1) nunca envía el correo a una cuenta pendiente de activación o inactiva — Better Auth por sí solo enviaría el reset a CUALQUIER cuenta que exista por email, sin mirar `isActive`/`activatedAt`; (2) límite de tasa dedicado (5/hora por correo normalizado + 20/hora por IP, `src/lib/rate-limit.ts`) además del límite global de Better Auth. La respuesta al cliente es SIEMPRE genérica salvo por "demasiadas solicitudes" (throttling, nunca revela existencia de cuenta). Token expira en 1 hora, un solo uso (`revokeSessionsOnPasswordReset: true` — cambiar la contraseña cierra las demás sesiones). Proveedor: Resend, ver "Envío de correo" más abajo.
- **Rate limiting de login:** habilitado (`rateLimit.enabled: true` en `src/lib/auth.ts`), storage `"memory"` — suficiente para una sola instancia de servidor (desarrollo/V1). **En producción con más de una instancia**, cambiar a `storage: "database"` o `"secondary-storage"` (ej. Redis) para que el límite se comparta entre procesos; con memoria cada instancia cuenta intentos por separado, debilitando la protección.

## Autenticación en dos pasos (MFA) — PREPRODUCCIÓN, MFA para ADMIN y operaciones financieras

- **Plugin OFICIAL de Better Auth (`better-auth/plugins` → `twoFactor`), nunca criptografía propia.** TOTP (RFC 6238, compatible con Google/Microsoft Authenticator, Authy, 1Password) + códigos de recuperación — ver `src/lib/auth.ts`. El secreto TOTP y los códigos de recuperación se cifran con `BETTER_AUTH_SECRET` (ya existente, ninguna clave nueva) — nunca en texto plano, nunca `returned` por la API. Sin SMS/email OTP: `otpOptions` se deja sin configurar a propósito (sin `sendOTP` configurado, el propio plugin rechaza ese método).
- **Modelo `TwoFactor`** (migración `027_two_factor_auth`) — forma NATIVA del plugin, un registro por usuario (`userId` único). `User.twoFactorEnabled` (mismo plugin) es la única fuente de verdad de "¿tiene MFA activo?"; nunca se activa hasta confirmar un código real (`skipVerificationOnEnable: false`).
- **Obligatorio para todo `role=ADMIN`, sin excepción — aplicado server-side en `src/lib/authorization.ts`, no solo en la UI.** `requireUser()` (páginas) y `requireSessionUser()`/`requireSessionRole()` (Server Actions/servicios) rechazan a un ADMIN sin MFA — la página redirige a `/mfa/setup`; el servicio lanza `AppError("MFA_REQUIRED")`. Como esto corre en la MISMA función que usan literalmente todos los Server Actions del proyecto, no hay una ruta alternativa que lo evite manipulando la URL o invocando la action directamente. AGENT/ASSISTANT nunca están sujetos a este requisito (MFA sigue siendo opcional/voluntario para ellos, gestionable desde `/settings/account`).
- **El primer ADMIN (bootstrap) también queda sujeto** — `twoFactorEnabled` nace en `false` por defecto, así que en su primer login cae en el mismo `/mfa/setup` que cualquier ADMIN nuevo.
- **Login con MFA:** contraseña correcta + `twoFactorEnabled=true` → el propio hook nativo del plugin borra la sesión recién creada y responde `twoFactorRedirect:true` (nunca se crea una sesión completa antes del segundo factor) → `/login/verify` pide TOTP o un código de recuperación. Mensajes siempre genéricos ("Código incorrecto.") — nunca distinguen vencido/reutilizado/incorrecto. Bloqueo de cuenta nativo tras 10 fallos consecutivos (`TwoFactor.failedVerificationCount`/`lockedUntil`, 15 minutos) — ver `node_modules/better-auth/dist/plugins/two-factor/verify-two-factor.mjs`.
- **Códigos de recuperación:** 10 por conjunto (mínimo pedido: 8), un solo uso cada uno, cifrados. Regenerar (`src/services/mfa.service.ts::regenerateBackupCodes`, exige contraseña + TOTP) invalida TODO el conjunto anterior y revoca las demás sesiones (nunca la actual). Nunca se envían por correo ni se ofrece una descarga automática — solo se muestran una vez en pantalla.
- **Step-up MFA para revelar métodos de pago (`payment-methods.service.ts::revealPaymentMethodFull`).** Contraseña + código TOTP se reverifican en LA MISMA llamada que revela — nunca se acepta un booleano del cliente como prueba de un desafío anterior. Guarda anti-replay propia (`src/lib/totp-replay-guard.ts`, en memoria): el mismo código TOTP no puede reutilizarse para revelar un SEGUNDO método de pago dentro de su ventana de validez — cierra el hueco real de que Better Auth no registra "último código usado" para esta ruta (sí lo hace para fallos de login, vía el bloqueo de cuenta ya descrito). Como todo ADMIN ya tiene MFA obligatorio antes de poder usar el CRM, este código siempre se exige, sin rama alternativa "si el ADMIN tiene MFA".
- **Desactivación:** exige contraseña + TOTP + confirmación explícita, revoca las demás sesiones, auditada (`MFA_DISABLED`). Un ADMIN NO puede desactivar su propio MFA si es el único ADMIN con MFA configurado (`src/services/mfa.service.ts::disableTotp`) — evita dejar el CRM sin ningún ADMIN capaz de operar con MFA; el mensaje dirige al procedimiento administrativo local.
- **Recuperación administrativa (pérdida total del autenticador):** `scripts/mfa-admin-recovery.ts` — herramienta LOCAL, nunca un endpoint HTTP. Requiere confirmación explícita escribiendo el correo exacto del usuario; asume que el operador ya verificó la identidad de esa persona por un medio FUERA del CRM (el script no lo hace ni puede hacerlo). Borra el `TwoFactor`, pone `twoFactorEnabled=false`, revoca todas las sesiones, audita (`MFA_ADMINISTRATIVE_RECOVERY`) sin exponer ningún secreto. El usuario deberá configurar MFA de nuevo antes de poder usar el CRM.
- **"Promover a ADMIN":** esta aplicación no tiene (ni tenía antes de este ticket) una función para cambiar el rol de un usuario existente — el único camino para que alguien sea ADMIN es crearlo así desde el inicio (`createUser` con `role: "ADMIN"`), que ya nace con `twoFactorEnabled=false` y sin sesiones previas que revocar. Si en el futuro se agrega un cambio de rol, deberá reproducir ese mismo criterio (forzar pendiente-MFA + revocar sesiones) — no se implementó aquí una función que no existe, para no exceder el alcance de esta ficha.
- **Auditoría:** `MFA_ENROLLMENT_STARTED`/`MFA_ENROLLMENT_COMPLETED`/`MFA_BACKUP_CODES_REGENERATED`/`MFA_DISABLED`/`MFA_ADMINISTRATIVE_RECOVERY`/`MFA_LOGIN_CHALLENGE_SUCCEEDED` — nunca el secreto, el código TOTP ni un código de recuperación. Los desafíos FALLIDOS de login no se duplican en `AuditEvent`: ya quedan cubiertos por `TwoFactor.failedVerificationCount`/`lockedUntil` (nativo, sin secretos) — intentar interceptarlos también en un hook global (`onAPIError`) no es viable en la versión instalada (ese hook recibe el `AuthContext` general, sin `.path`/`.session` fiables por request).
- **Rate limiting propio, además del nativo del plugin (3 cada 10s en todo `/two-factor/*`):** enrollment/regenerar/desactivar, 5 intentos / 15 minutos por usuario (`src/services/mfa.service.ts`, reutiliza `src/lib/rate-limit.ts`).
- **Nunca en `localStorage`/`sessionStorage`.** El secreto/QR/códigos de recuperación viven únicamente en el estado de React del componente de enrollment mientras se muestran una vez — nunca se guarda la imagen QR en archivo, base de datos o almacenamiento persistente.
- **Riesgo residual aceptado y documentado:** un código TOTP reutilizado dentro de su propia ventana de ~30-90s para un SEGUNDO intento de LOGIN (no de step-up financiero, que sí tiene guarda) solo podría volver a autenticar al MISMO usuario legítimo — no hay escalamiento de privilegio ni acceso a un recurso distinto, y ya hay rate limiting + bloqueo de cuenta sobre intentos repetidos.

## Envío de correo (PREPRODUCCIÓN — Correos, invitaciones y recuperación de acceso)

- **Proveedor:** Resend, vía su API REST directa (`fetch`, sin SDK adicional) — `src/lib/email.ts`. Interfaz `EmailTransport` desacoplada del proveedor real, para poder cambiarlo después sin tocar los flujos que lo usan.
- **Variables requeridas:** `RESEND_API_KEY`, `EMAIL_FROM`; opcional `EMAIL_REPLY_TO`. `APP_URL` (o, como respaldo, `BETTER_AUTH_URL`) es la URL pública usada para construir cualquier enlace de un correo — validada al usarse (`src/lib/env.ts`): debe ser HTTPS cuando `NODE_ENV=production`. Ninguna se hardcodea ni se expone en logs/errores — si falta alguna, el envío falla con un error claro, **nunca se simula un envío exitoso**.
- **Verificación de dominio:** ver [`docs/EMAIL_RESEND_SETUP.md`](./EMAIL_RESEND_SETUP.md) para los registros DNS necesarios para `tuplansegurousa.com` — documentación únicamente, ningún cambio de DNS se realizó.
- **Plantilla única** (`src/lib/email-templates.ts`) para todos los correos transaccionales — marca azul/naranja, texto plano equivalente, botón + URL completa como alternativa, aviso de "ignora este correo si no lo solicitaste". Todo el contenido dinámico (nombres, correos) pasa por `escapeHtml()` antes de interpolarse — nunca se permite inyección de HTML desde un campo de usuario. Nunca incluye datos de clientes/pólizas/pagos/SSN/EAD/información médica.
- **En pruebas nunca se hace una llamada de red real** — `vitest.setup.ts` instala un transport no-op globalmente para TODA la suite; un test que necesite inspeccionar el contenido de un mensaje instala su propio doble y lo restaura a ese no-op al terminar (nunca al transport real).
- **En desarrollo, sin `RESEND_API_KEY`/`EMAIL_FROM` configurados**, cualquier flujo que necesite enviar un correo falla con un error claro (nunca simula éxito). Para probar el flujo de activación sin correo configurado, `npm run dev:issue-local-link -- --email=...` emite una invitación nueva e imprime el enlace en la terminal — bloqueado incondicionalmente si `NODE_ENV=production`, nunca escribe el enlace en un archivo o log persistente.

## Autorización

- **Server-side, siempre.** `src/lib/authorization.ts` expone `requireUser()`/`requireRole(...roles)` (redirigen, para páginas) y `requireSessionUser()`/`requireSessionRole(...roles)` (lanzan `AppError`, para la capa de servicios — ver `docs/ARCHITECTURE.md`). Todas vuelven a consultar `User.role`/`isActive` en Prisma en cada llamada — nunca confían en los datos de sesión cacheados por Better Auth ni en lo que el cliente envíe (`userId`, `role`, etc. nunca se aceptan desde el request).
- **Cada servicio exige `actor: AuthorizedUser` explícito, nunca lo resuelve internamente.** El único lugar que construye un `AuthorizedUser` legítimo es `requireSessionUser()`/`requireSessionRole()`. La regla de permiso sobre la operación concreta (ej. qué puede editar un AGENT) vive dentro del servicio mismo, no en el llamador — no se puede saltar reutilizando el servicio desde otro lugar sin modificar el servicio.
- **Sin endpoints de prueba dejados en el código.** `/api/admin-check`, creado exclusivamente para verificar `requireRole()` en la Fase 007, se eliminó al iniciar la Fase 008 — no debe quedar como precedente dejar rutas de verificación accesibles.
- **`User.isActive = false` bloquea acceso de inmediato en la siguiente petición protegida**, aunque la cookie de sesión siga siendo técnicamente válida — verificado en pruebas (ver `docs/DECISIONS.md`). No hay revocación instantánea vía WebSocket (no necesaria para V1); el usuario pierde acceso en cuanto hace la siguiente petición a una ruta protegida, típicamente segundos después de la desactivación, no al expirar la sesión.
- **El Proxy (`src/proxy.ts`) hace solo una verificación optimista** (existencia de cookie, sin tocar la base de datos) para redirigir rápido a `/login` — la verificación real (sesión válida + `isActive`) ocurre siempre en `requireUser()`/`requireRole()` dentro de la página o Route Handler. Nunca depender solo del Proxy para proteger datos sensibles.
- **Matriz de roles inicial:** `ADMIN` (acceso total), `AGENT` y `ASSISTANT` (clientes, hogares, pólizas, tareas, cumpleaños; acceso financiero/salud a definir por regla específica cuando se construyan esos módulos). Reglas granulares por módulo se implementan cuando cada módulo se construya, no de forma anticipada. **Excepción explícita desde Fase 016:** Comisiones es el único módulo donde ASSISTANT no tiene ningún acceso (ni lectura ni escritura) — ver sección "Comisiones — Fase 016" más abajo.

## Medicamentos y proveedores/médicos preferidos (`PersonMedication`/`PersonProvider`) — Fase 019.8

Clasificación: información operacional de salud, más sensible que el resto del CRM (el CRM no es un sistema clínico).

- **Autorización: `canEditPerson`** (misma regla que editar cualquier otro dato de un contacto — ADMIN/ASSISTANT sin restricción de asignación, AGENT solo si tiene acceso al contacto), aplicada tanto a lectura como a escritura en `health-records.service.ts`. Deliberadamente más estricta que ver el perfil básico de un contacto (Fase 008, abierto a cualquier usuario activo) — se decidió que incluso LEER esta información debiera seguir la regla de asignación, no solo escribirla.
- **Viven en `Person`, nunca en `Policy`.** Una persona puede cambiar de póliza y su historial de medicamentos/proveedores debe permanecer — nunca se consultan ni se muestran desde el contexto de una `Policy`.
- **Nunca se exponen fuera de la sección "Salud" del perfil de contacto** — no aparecen en tablas generales de contactos, el Dashboard, resultados de búsqueda global, ni notificaciones/resúmenes automáticos (mismo principio ya aplicado a `HealthPolicyDetail`).
- **`CommissionExpectation`/`CommissionPayment` ya se implementaron en Fase 016 — ver esa sección para las reglas reales.**

## `HealthPolicyDetail` — Fase 013

Clasificación: **SENSIBLE / FINANCIERO relacionado con salud**. Particularmente `incomeUsed` (ingreso usado en la aplicación de Marketplace) y `taxCreditAmount` (crédito fiscal): son datos financieros personales del cliente, no datos operativos del plan.

- **Autorización server-side, nunca solo ocultar en UI.** `health-policies.service.ts` reutiliza exactamente `assertCanAccessPolicy` (misma política que `Policy`) para ver/crear/editar: ADMIN y ASSISTANT sin restricción de asignación, AGENT solo si tiene acceso al titular o a algún miembro cubierto.
- **ASSISTANT nunca recibe `incomeUsed`/`taxCreditAmount` en la respuesta del servicio.** `getHealthPolicyDetail` omite esas dos propiedades del objeto devuelto para ASSISTANT (no solo las pone en `null` — la clave ni siquiera existe en el objeto), y ese objeto ya redactado es lo único que llega al Client Component. `createHealthPolicyDetail`/`updateHealthPolicyDetail` rechazan explícitamente (`FORBIDDEN`) cualquier intento de ASSISTANT de escribir esos dos campos, incluso si el request los incluye a mano — la UI simplemente no renderiza esos inputs para ASSISTANT, pero esa omisión es conveniencia, no el control real.
- **Resto de campos** (`marketplaceApplicationId`, `marketplaceState`, `planNameSnapshot`, deducibles, out-of-pocket) se consideran datos administrativos/del plan, no financieros personales — ASSISTANT los lee y escribe sin restricción.
- **No debe aparecer en listados generales.** `listPolicies`, `getPoliciesForPerson` y el `getPolicyById` básico (usado por `/policies`, el tab "Pólizas" de un contacto, y el resumen de `/policies/[id]`) **nunca** incluyen `HealthPolicyDetail` — se consulta únicamente vía `getHealthPolicyDetail`, llamado explícitamente solo desde la sección "Información del plan de salud" de `/policies/[id]` y desde `/policies/[id]/health`. Verificado en tests (`health-policies.service.test.ts`, casos U/V): ni el listado de pólizas ni el detalle básico de una póliza exponen la clave `healthDetail`.
- **`incomeUsed`/`taxCreditAmount` nunca deben registrarse en logs** — igual que el resto de montos financieros del proyecto (ver principio general en la sección de Comisiones de `docs/DECISIONS.md`), un log de error debe referenciar el `id` de la póliza, nunca los valores del `HealthPolicyDetail`.
- **`HealthPolicyDetail` solo existe para `Policy.product.policyType === HEALTH`**, validado en el servicio (`assertIsHealthPolicy`) antes de crear/editar — nunca mediante trigger de base de datos (mismo patrón que la regla equivalente documentada en la migración 002).

Reglas específicas para `PersonProvider`/`PersonMedication` (información médica operacional, más sensible que el resto del CRM — el CRM no es un sistema clínico, ver [DECISIONS.md](./DECISIONS.md)):

- **Autorización server-side obligatoria** en cualquier endpoint/acción que lea o escriba estas tablas — nunca confiar solo en ocultar la UI.
- **No deben aparecer en logs normales de aplicación** (logs de requests, errores genéricos, etc.). Si un log necesita referenciar una de estas filas, usar su `id`, nunca su contenido (`name`, `dosage`, `notes`).
- **No deben exponerse en el frontend fuera de una sección dedicada y protegida.** Cuando se construya el perfil de persona ("Person Profile"), Salud/Health debe ser una sección separada del resto de la información de contacto — no debe aparecer en:
  - tablas generales de contactos/clientes,
  - el dashboard,
  - resultados de búsqueda global,
  - notificaciones o resúmenes automáticos.
- **No usar esta información para inferir diagnósticos o condiciones médicas** no registradas explícitamente — el sistema no debe "adivinar" nada a partir de un nombre de medicamento.
- Aplica el mismo principio de minimización de datos del resto del proyecto: no agregar campos a estas tablas sin una necesidad operacional clara y evaluada explícitamente.

## Credenciales y datos de pago

- El CRM nunca almacena contraseñas de portales de aseguradoras ni credenciales de Marketplace en texto plano — ver la sección "Vault de credenciales de portal" más abajo.
- **Excepción explícita, acotada — AMPLIACIÓN PREPRODUCCIÓN (Métodos de pago cifrados):** desde esta fase el CRM SÍ almacena el número completo de tarjeta y el número de cuenta/routing bancario, pero **cifrados** (nunca en texto plano), **exclusivamente** en el modelo `PaymentMethod`, con acceso restringido a `role=ADMIN` sin excepción. **CVV/CVC/CID, PIN y track data NUNCA se almacenan** — no existe columna para ninguno de los tres en ningún modelo del proyecto. Ver la sección "Métodos de pago cifrados" más abajo para el detalle completo.
- `User` (usuario interno) ya tiene autenticación (Better Auth); ver sección "Autenticación" arriba para el detalle.

## Métodos de pago cifrados (`PaymentMethod`) — AMPLIACIÓN PREPRODUCCIÓN

Clasificación: **FINANCIERO / MÁS SENSIBLE DEL CRM** — a diferencia de Comisiones (ingresos de la agencia) o `HealthPolicyDetail` (datos personales), aquí se almacena el número completo de un instrumento de pago del cliente. Todo lo siguiente es más estricto que cualquier otro módulo existente.

- **Cifrado — `src/lib/financial-crypto.ts`, NO el vault de `pii-crypto.ts`.** Se investigó reutilizar `pii-crypto-core.ts` (usado hoy para SSN/USCIS/credenciales de portal) y se determinó que NO cumple los requisitos de este ticket: usa una única llave global sin AAD (Additional Authenticated Data) y sin separación de contexto por dominio. En vez de inventar cifrado nuevo, se derivó una subclave de dominio financiero vía **HKDF-SHA256** (`node:crypto.hkdfSync`, RFC 5869 — primitiva estándar, no criptografía propia) a partir de la MISMA `PII_ENCRYPTION_KEY` maestra, con un "info" fijo (`"tuplanseguro-financial-v1"`) usado también como AAD en AES-256-GCM. Resultado: un ciphertext financiero (prefijo `fin-v1:`) nunca es interpretable como un ciphertext de `pii-crypto` (prefijo `v1:`) ni viceversa, aunque compartan la llave maestra — verificado en `financial-crypto.test.ts` con una prueba dedicada de separación de contexto.
- **Campos cifrados:** número de tarjeta, routing number, número de cuenta bancaria, y el comentario administrativo. Se guarda por separado el `last4` (los últimos 4 dígitos) en texto plano para poder mostrar "Visa •••• 1234" sin descifrar. La dirección de facturación se guarda en texto plano (mismo criterio que `Household.address*` — no es un dato de pago).
- **Prohibido por diseño — nunca almacenado:** CVV/CVC/CID, PIN, track data. No existe columna para ninguno en `PaymentMethod` ni en ningún otro modelo — si un formulario o llamada a la API intentara mandarlos, el schema de Zod los descarta silenciosamente (no son campos reconocidos), nunca se persisten.
- **Autorización de UN SOLO NIVEL — SOLO `role=ADMIN`, sin excepción:** crear, editar, ver, revelar y desactivar métodos de pago exige `ADMIN`. Ser `ADMIN` y además agente (`isAgent=true`) no relaja esta regla (no hace falta: ya es ADMIN). AGENT y ASSISTANT son rechazados server-side (`FORBIDDEN`) en las 8 funciones de `payment-methods.service.ts`, verificado en tests aunque se intente invocar directamente la Server Action. La pestaña "Pagos" del perfil de contacto ni siquiera se renderiza para AGENT/ASSISTANT (más estricto que la pestaña "Comisiones", que sí es visible para AGENT).
- **Revelar exige, en este orden:** (1) reautenticación con la contraseña actual del ADMIN vía el endpoint real de Better Auth (`auth.api.verifyPassword`, con `sensitiveSessionMiddleware`) — nunca una comparación de contraseña propia; (2) un motivo obligatorio (mínimo 3 caracteres) y, opcionalmente, la póliza relacionada; (3) rate limiting (10 intentos / 15 minutos por usuario, `checkRateLimit`); (4) recién entonces se descifra — nunca antes de validar los tres pasos anteriores. **CORRECCIÓN**: una sola reautenticación revela el CONJUNTO COMPLETO de datos del método (`revealPaymentMethodFull` — antes revelaba un campo a la vez, insuficiente para completar un pago real en el portal de la aseguradora, que necesita nombre + número + vencimiento juntos, o routing + cuenta juntos). Los datos revelados nunca se cachean ni se persisten en el navegador; la UI los oculta automáticamente a los 20 segundos y también al cerrar la ventana. Cada campo tiene su propio botón de copiar individual — nunca un botón de "copiar todo" — y cada copia se audita por separado (`PAYMENT_METHOD_FIELD_COPIED`: usuario, método, nombre del campo) sin registrar jamás el valor copiado, igual que el vault de credenciales de portal. Cada revelación se audita (`PAYMENT_METHOD_REVEALED`: usuario, método, póliza, motivo, y la lista de nombres de campo revelados) **sin registrar jamás ningún valor revelado o copiado**.
- **MFA — implementado para "revelar" (PREPRODUCCIÓN, MFA para ADMIN y operaciones financieras).** `revealPaymentMethodFull` exige contraseña + código TOTP en la misma llamada (ver sección "Autenticación en dos pasos (MFA)" arriba) — `replacePaymentMethodSecret` sigue exigiendo solo contraseña (fuera del alcance explícito de esa ficha, que solo pedía step-up para "revelar tarjetas o cuentas bancarias").
- **Edición segura (nunca parcial):** el formulario de edición de metadata NUNCA recibe el número completo (ni siquiera para precargarlo oculto en el HTML). Cambiar un número de tarjeta/cuenta exige la misma reautenticación que revelar, y siempre reemplaza el valor COMPLETO — no existe una operación de "editar parcialmente" el ciphertext. Si la operación falla, no se persiste ningún valor parcial (todo dentro de una transacción de Prisma).
- **Revocar preserva la auditoría — nunca borra la fila.** `revokePaymentMethod` pone `isActive=false`, `isDefault=false`, `autopay=false` y fija `revokedAt`, pero conserva el registro completo (incluidos los campos de consentimiento histórico) para que la auditoría permanezca íntegra.
- **Consentimiento:** se registra si el cliente autorizó conservar el método, la fecha, el uso autorizado (`AUTOPAY`/`PAYMENT_ASSISTANCE`/`BOTH`) y quién lo registró. Activar `autopay=true` sin `consentGiven=true` se rechaza server-side (`VALIDATION_ERROR`), no solo en el formulario.
- **El CRM nunca ejecuta cobros con estos datos.** Se almacenan únicamente para ayudar a configurar el pago en el portal de la aseguradora — no existe ninguna integración de procesamiento de pagos en este proyecto.
- **Comentario administrativo:** máximo 1,000 caracteres, cifrado igual que los demás campos sensibles (defensa en profundidad, aunque sea "solo" una nota), sanitizado (se elimina cualquier etiqueta HTML antes de guardar), y nunca incluido en exportaciones generales. La UI advierte explícitamente no escribir CVV/PIN/contraseñas/SSN/números completos en este campo.
- **Nunca aparece en logs, `AuditEvent.metadata`, URLs, mensajes de error, analítica ni en ningún export CSV/XLSX existente.** Los audit events de este módulo (`PAYMENT_METHOD_CREATED/UPDATED/SET_DEFAULT/REVOKED/REVEALED/SECRET_REPLACED`) solo registran metadatos operativos (campo afectado, motivo, política relacionada) — nunca el valor cifrado ni el valor en claro.
- **Rotación de claves — bloqueo documentado, no implementado.** El formato versionado (`fin-v1:...`) permite en el futuro migrar a `fin-v2` sin reescribir el descifrador existente, pero no existe hoy una rutina que reencripte filas existentes bajo una clave nueva. Igual que el vault de SSN/USCIS (`pii-crypto.ts`), esta es una limitación aceptada y documentada, no un olvido.
- **Manipulación del ciphertext se rechaza de forma segura.** Al ser AES-256-GCM (cifrado autenticado), cualquier alteración del ciphertext, el IV o el authTag hace que el descifrado falle con un error genérico — nunca se retorna un valor parcial o corrupto al llamador.

## Documentos de póliza (`PolicyDocument`) — Fase 019.5

Clasificación: **operativo**, no financiero-restringido (a diferencia de Comisiones) — ASSISTANT sí participa.

- **Nunca se guarda el binario en PostgreSQL.** `PolicyDocument` es solo metadata; el archivo vive en el `FileStorage` abstraído (`src/lib/storage.ts`) — en desarrollo, fuera de `/public` (`private-storage/`, gitignored); en producción requiere un adapter S3-compatible todavía no implementado (deliberadamente, ver `docs/DECISIONS.md`).
- **Nunca URLs públicas permanentes.** Toda descarga/visualización pasa por `GET /api/policies/[id]/documents/[documentId]` (Route Handler), que llama `requireSessionUser()` y vuelve a verificar autorización de la póliza (`assertCanAccessPolicy`) en cada request — conocer la URL/el `documentId` nunca es suficiente por sí solo.
- **El tipo real del archivo se verifica por firma binaria, nunca por extensión ni por el `Content-Type` declarado por el navegador.** `src/lib/file-sniff.ts` implementa detección real de magic bytes (PDF `%PDF`, PNG, JPEG, WEBP) — un archivo `.exe` renombrado a `.pdf` se rechaza aunque el navegador diga `application/pdf`.
- **Allow-list, no deny-list.** `ALLOWED_DOCUMENT_MIME_TYPES` lista únicamente PDF/PNG/JPEG/WEBP — cualquier otro tipo (incluidos `.exe`/`.js`/`.html`/`.svg`) se rechaza automáticamente sin necesidad de enumerarlo.
- **`storageKey` siempre generado (`crypto.randomUUID()` + extensión derivada del MIME ya verificado), nunca el nombre de archivo original** — es el mecanismo real que impide path traversal, reforzado con validación de patrón estricto en `LocalFileStorage.resolveSafePath()` como defensa en profundidad.
- **Tamaño máximo 15MB**, validado antes de escribir a disco.
- **Autorización igual que `Policy`** (`assertCanAccessPolicy`), no una regla más estricta como Comisiones — ASSISTANT puede subir/ver/eliminar documentos operativos en cualquier póliza a la que ya tenga acceso.

Comparte el mismo invariante "solo CREATE, nunca UPDATE" que la generación manual — no requiere ni agrega ninguna autorización nueva, porque nunca se invoca directamente desde una request de un usuario sin pasar antes por la autorización propia de esa acción (crear póliza, editar prima, etc.).

## Administración de usuarios (Configuración → Usuarios) — Fase 019.5

- **El ADMIN nunca define ni conoce la contraseña de un usuario nuevo** (superó la "contraseña temporal" de una fase anterior) — `createUser` crea `User`+`Account` (`password: null`) y emite una invitación de un solo uso por correo; ver "Invitación y activación de cuentas" abajo para el detalle completo del mecanismo.

Invalida todas las sesiones activas del usuario objetivo (`session.deleteMany`), forzando un nuevo login. La contraseña nunca se registra en `AuditEvent` (acción `USER_PASSWORD_RESET`, metadatos limitados a `targetUserId`) ni se imprime en ningún lado — nunca se puede recuperar la contraseña anterior, solo establecer una nueva.

## Invitación y activación de cuentas (PREPRODUCCIÓN — Correos, invitaciones y recuperación de acceso)

- **Reutiliza la tabla `Verification` de Better Auth** (`identifier = "invite:<userId>"`) en vez de un modelo nuevo — `src/services/user-invitations.service.ts`.
- **El token real NUNCA se persiste en claro** — solo su hash SHA-256 (`Verification.value`). El token viaja exclusivamente en el enlace del correo; sin el correo, no hay forma de recuperar un enlace ya emitido (ver `npm run dev:issue-local-link` para pruebas locales, que EMITE uno nuevo, nunca "recupera" el anterior).
- **Expiración: 24 horas.** Un token nuevo (invitación inicial o reenvío) borra cualquier fila anterior con el mismo `identifier` antes de insertar la nueva — un enlace previo deja de ser válido de inmediato, sin necesitar una columna de "invalidado".
- **ADMIN-only para crear/reenviar/revocar** (`assertAdminOnly`). Reenviar SIEMPRE genera un token nuevo (invalida el anterior). Revocar (`revokeInvitation`) borra la fila de `Verification` sin emitir uno nuevo — idempotente, nunca falla si ya no había invitación pendiente.
- **Un usuario pendiente (`activatedAt = null`) no puede iniciar sesión** — su `Account.password` es `null`, así que el login de Better Auth lo rechaza de forma nativa (mismo mecanismo, sin lógica adicional).
- **`createUser` rechaza un correo que ya pertenece a una cuenta existente** (`email` es `@unique` en `User`, normalizado a minúsculas por el propio schema de Zod — `createUserSchema.email: z.email().trim().toLowerCase()`) con un mensaje seguro genérico, nunca distingue "existe y está activa" de "existe y está pendiente".
- **Rate limiting propio** (`src/lib/rate-limit.ts`, independiente del de Better Auth, que no cubre estas rutas): reenvío 5/hora por ADMIN; activación 10 intentos/15min por invitación **+** 30/15min por IP (evita probar tokens contra muchas invitaciones distintas desde la misma IP).
- **Auditoría de creación/reenvío/revocación/activación** (`USER_CREATE`, `USER_INVITATION_RESENT`, `USER_INVITATION_REVOKED`, `USER_ACTIVATED`) — nunca el token ni la contraseña.
- **Correo enviado DESPUÉS de confirmar la transacción de DB, nunca dentro de ella** — si el envío falla (proveedor no configurado, error de red), el usuario y el token YA quedaron creados; el ADMIN puede usar "Reenviar invitación" en cuanto el correo esté configurado, sin duplicar la creación ni la auditoría.
- **Aviso de activación**: al completar la activación se envía un correo de cortesía confirmando que la cuenta ya está activa — mejor esfuerzo, nunca revierte una activación ya confirmada si el envío falla.

## Autoservicio de cuenta — cambio de contraseña/correo (PREPRODUCCIÓN)

`src/services/account-security.service.ts`, `/settings/account` — para CUALQUIER usuario ya autenticado (ADMIN/AGENT/ASSISTANT), distinto de "olvidé mi contraseña" (sin sesión) y de "ADMIN restablece la contraseña de otro usuario" (administrativo).

- **Cambiar contraseña** usa el endpoint nativo `auth.api.changePassword` — exige la contraseña ACTUAL (la valida el propio endpoint), y `revokeOtherSessions: true` cierra cualquier otra sesión abierta en otro dispositivo/navegador (la sesión actual permanece válida). Envía un correo de confirmación (mejor esfuerzo) y audita `USER_PASSWORD_SELF_CHANGED`.
- **Cambiar correo** usa el endpoint nativo `auth.api.changeEmail`, protegido nativamente por `sensitiveSessionMiddleware` (Better Auth exige una sesión "fresca"). Esta capa AGREGA una reautenticación explícita con la contraseña actual (`auth.api.verifyPassword`, mismo patrón ya usado en `payment-methods.service.ts`) para no depender únicamente de esa semántica interna. El correo NO cambia de inmediato: `emailVerification.sendVerificationEmail` (`src/lib/auth.ts`) envía una confirmación a la dirección NUEVA; el cambio solo se aplica cuando esa confirmación se completa (`afterEmailVerification`, que audita `USER_EMAIL_CHANGED` y avisa a la dirección nueva). El aviso a la dirección ANTERIOR se envía de inmediato al solicitar el cambio (nunca se espera a la confirmación) para que el dueño legítimo se entere de la solicitud tan pronto ocurre.
- **ADMIN no puede conocer ni establecer directamente la contraseña de otro usuario** a través de este flujo — `resetUserPassword` (administrativo, Fase 022) sigue siendo la única vía, y sigue siendo unidireccional (nunca expone/recupera la anterior).
- **Rate limiting propio**: 5 intentos/15min por usuario, tanto para cambio de contraseña como de correo.

## Riesgos pendientes antes de producción

- **Rate limiting con storage `"memory"`** no protege contra fuerza bruta distribuida entre múltiples instancias del servidor — cambiar a `"database"`/Redis antes de escalar horizontalmente.
- **Sin HTTPS forzado todavía** a nivel de aplicación (depende de dónde se despliegue) — `Secure` en cookies solo se activa cuando el entorno es de producción según la detección de Better Auth; confirmar que el proxy/balanceador de producción sirva siempre sobre HTTPS.
- **MFA implementado para ADMIN y para revelar métodos de pago** (ver sección dedicada arriba) — pendientes reales antes de producción: rate limiting sigue en memoria (mismo riesgo de siempre, no específico de MFA); `replacePaymentMethodSecret` (reemplazar número) NO tiene step-up TOTP todavía, solo contraseña; SSN/USCIS (`sensitive-identity.service.ts`) tampoco tiene step-up TOTP — ninguno de los dos estaba en el alcance de esta ficha.
- **Sin auditoría de intentos de login fallidos** más allá de los logs por defecto de Better Auth — el `AuditEvent` implementado en Fase 019.9 (ver más abajo) NO cubre autenticación (login/logout, intentos fallidos), solo acciones de negocio ya autenticadas; sigue pendiente si se decide auditar también el acceso.
- **Dominio de correo (`tuplansegurousa.com`) todavía no verificado en Resend** — ver [`docs/EMAIL_RESEND_SETUP.md`](./EMAIL_RESEND_SETUP.md). Sin verificarlo, `EMAIL_FROM` debe usar un dominio ya verificado (ej. el de prueba de Resend) o el envío fallará.
- **`RESEND_API_KEY`/`EMAIL_FROM`/`APP_URL` de producción todavía no configurados** — este ticket no los define (fuera de alcance: "no cambios en producción"); el checklist de despliegue debe incluir configurarlos y verificar `APP_URL` con HTTPS antes de servir tráfico real.

## Audit Trail (`AuditEvent`) — Fase 019.9

Detalle funcional completo (qué se audita, formato, servicio central) en [AUDIT_TRAIL.md](./AUDIT_TRAIL.md). Aquí solo las propiedades de seguridad.

- **Append-only por construcción de código, no por permiso de base de datos.** No existe ninguna función `updateAuditEvent`/`deleteAuditEvent` en `audit.service.ts`, ni ninguna ruta/Server Action que las exponga — la única operación posible desde la aplicación es `create`. Un mantenimiento técnico que requiriera tocar filas existentes (ej. una corrección de datos) tendría que hacerse fuera de la aplicación, de forma documentada, nunca vía una UI de "editar historial" (que deliberadamente no existe).
- **Atribución real del actor**: `actorUserId` es una FK a `users`, nunca solo un nombre en texto — el timeline muestra `actor.name` resuelto en el momento de consultar, así que un usuario renombrado se refleja correctamente en eventos pasados (a diferencia de si se hubiera guardado el nombre como string suelto). `actorType: SYSTEM` (con `actorUserId = null`) se usa exclusivamente cuando no hay un actor humano real — nunca se atribuye una acción del sistema a un usuario por conveniencia.
- **Minimización de PII/PHI de forma estructural, no solo por convención**: los campos auditables de cada entidad son una allowlist explícita pasada a `buildDiff()` (`PERSON_AUDIT_FIELDS`, `POLICY_AUDIT_FIELDS`, `HOUSEHOLD_AUDIT_FIELDS`, `HEALTH_DETAIL_AUDIT_FIELDS`, `TASK_AUDIT_FIELDS`, `PREMIUM_AUDIT_FIELDS`) — un campo que no está en esa lista no puede aparecer en `changes` aunque el objeto `before`/`after` completo lo contenga. `incomeUsed`/`taxCreditAmount` (financiero personal), montos de comisiones/pagos (financiero restringido, Fase 016), y nombre/dosis/notas de medicamentos/proveedores (salud operacional) están excluidos de sus respectivas allowlists — esos eventos se generan igual (para saber QUE algo cambió, quién y cuándo) pero sin `changes`, o con `changes` limitado a los campos no sensibles del mismo registro.
- **Nunca contenido de archivos ni texto de notas** — `DOCUMENT_UPLOAD`/`DOCUMENT_DELETE` solo guardan `fileName` (metadata ya pública dentro de la aplicación, nunca los bytes); `NOTE_CREATE` nunca incluye `content`.
- **Autorización del timeline reutiliza exactamente la autorización ya establecida de cada entidad** (`canEditPerson` para contactos, `assertCanAccessPolicy` para pólizas) — nunca una regla nueva y paralela que pudiera desincronizarse. ASSISTANT excluido de eventos de Comisiones en el timeline por el mismo principio que en el módulo de Comisiones (Fase 016): FORBIDDEN total, sin excepción por contexto.
- **Transaccional con la escritura real** (`prisma.$transaction`) cuando es razonable — evita el escenario de un cambio real sin su evento correspondiente (o viceversa). Ver "Transaccionalidad" en `AUDIT_TRAIL.md` para el detalle de por qué las queries dentro de esas transacciones son siempre secuenciales (nunca `Promise.all`), consistente con el hallazgo de concurrencia de `pg` de Fase 019.6.

## Exportación CSV y conciliación de comisiones — Fase 020

- **Exportación CSV nunca amplía lo que el usuario ya puede ver.** `exportContactsCsv`/`exportPoliciesCsv`/`exportCommissionsCsv` reutilizan exactamente la misma autorización que sus listados normales (`policyAgentAccessWhere`, `agentCommissionAccessWhere`) — un CSV nunca contiene una fila que ese usuario no vería ya en `/contacts`, `/policies` o `/commissions`. **ASSISTANT nunca puede exportar Comisiones** (`FORBIDDEN` inmediato, misma exclusión total de Fase 016).
- **El CSV nunca incluye SSN, datos bancarios/tarjeta, credenciales, contenido de documentos, texto de notas, ni nombre/dosis/notas de medicamentos o proveedores** — las columnas exportadas son una lista explícita y corta por módulo (ver `export.service.ts`), nunca un `SELECT *` volcado a CSV. Verificado con tests que buscan explícitamente ausencia de esas palabras clave en el CSV generado (`export.service.test.ts`).
- **Límite de filas (`EXPORT_ROW_LIMIT = 5000`)** documentado en código — evita uso de memoria sin límite; suficiente para la escala de una sola agencia en V1.
- **El audit log de una exportación nunca guarda el contenido exportado** — solo actor, tipo, fecha, filtros seguros aplicados y un conteo aproximado (`EXPORT_CONTACTS`/`EXPORT_POLICIES`/`EXPORT_COMMISSIONS`, ver `AUDIT_TRAIL.md`).
- **Conciliación de comisiones es ADMIN-only en su totalidad** (subir, ver vista previa, emparejar, ignorar, aplicar) — decisión explícita documentada en `docs/DECISIONS.md`. AGENT conserva su acceso ya existente y acotado a sus propias comisiones (sin cambios); ASSISTANT sigue sin acceso al módulo de Comisiones en absoluto.
- **Archivos de reporte de comisión**: extensión validada contra el adaptador, tamaño máximo 5 MB, firma binaria verificada para `.xlsx` (`looksLikeZipArchive`) antes de parsear — nunca se confía en el nombre de archivo ni en el `Content-Type` declarado por el navegador (mismo principio que `file-sniff.ts` ya establecido para documentos de póliza). El archivo original nunca se guarda en la base de datos.
- **"Ver actividad" de un usuario (Configuración → Usuarios) es ADMIN-only** (`getUserActivity` en `history.service.ts`) — reutiliza la misma redacción/allowlist de `AuditEvent` ya vigente, nunca expone el JSON crudo de `changes`/`metadata` sin pasar por el mismo renderizado que el resto del Historial.

## Identidad sensible del contacto — Fase 021

Detalle funcional completo en [SENSITIVE_PII.md](./SENSITIVE_PII.md). Aquí solo las propiedades de seguridad, siguiendo la clasificación de PII pedida por la ficha (§49).

### Clasificación de PII

- **Máxima sensibilidad, cifrado recuperable obligatorio**: SSN, USCIS/A-Number, número de documento migratorio.
- **Alta sensibilidad, sin cifrar (controles de autorización + minimización, no criptografía)**: medicamentos, proveedores/médicos preferidos (Fase 019.8), `incomeUsed`/`taxCreditAmount` (Fase 016).
- **Administrativa, no PII identificatoria por sí sola**: `ImmigrationCategory`, tipo de documento, fechas de emisión/vencimiento — exportables en reportes; nunca los identificadores anteriores.

### SSN / USCIS / número de documento

- **Cifrado autenticado en reposo (AES-256-GCM), nunca hash irreversible** — el negocio necesita recuperar el valor completo para operaciones de Marketplace. `src/lib/pii-crypto.ts` es el único punto de cifrado/descifrado que usa la aplicación (Server Components/Actions/servicios) para este tipo de dato. Desde Fase 023, la implementación real vive en `src/lib/pii-crypto-core.ts` (sin el guard `"server-only"`, para que el importador de libro de negocio — un script de Node/tsx fuera del árbol de Next — pueda usar exactamente el mismo cifrado); `pii-crypto.ts` sigue siendo el único punto de entrada para el resto de la app.
- **Documento migratorio sin número: rechazado (Fase 023, Hallazgo #1 de UAT).** `PERMANENT_RESIDENT_CARD`/`EMPLOYMENT_AUTHORIZATION_DOCUMENT`/`OTHER` exigen `documentNumber` no vacío al CREAR (validado en schema Zod + UI con `required`) — antes se podía crear un documento vacío. Editar sigue permitiendo omitir `documentNumber` (significa "no lo toques", nunca crea un documento nuevo sin número).
- **`PII_ENCRYPTION_KEY`**: 32 bytes en base64, nunca en base de datos/repo/`NEXT_PUBLIC_*`/logs/`AuditEvent`. Local en `.env` (gitignored) para desarrollo; secreto de producción generado e independiente (nunca reutilizado entre entornos, mismo principio ya aplicado a `BETTER_AUTH_SECRET`).
- **Enmascarado por defecto en TODA superficie** (Contact Detail, resumen, reporte de clientes) — `***-**-6789` / `*****1234` / `******9876`. El valor completo solo se calcula server-side cuando el usuario pulsa "Mostrar", vía una Server Action dedicada (nunca en la carga inicial de la página, nunca en HTML/props/hidden inputs/query strings).
- **Autorización de revelar/gestionar es un gate propio (`canAccessSensitiveIdentity`), nunca `canEditPerson`** — ADMIN siempre, AGENT solo con acceso operativo al contacto, ASSISTANT NUNCA (ni para registrar la categoría migratoria). Ver `docs/SENSITIVE_PII.md`.
- **Revelar se audita siempre** (`SSN_REVEALED`/`USCIS_REVEALED`/`IMMIGRATION_DOCUMENT_REVEALED`) — nunca con el valor en el summary/metadata.
- **Nunca cacheable**: las Server Actions de reveal se ejecutan como POST bajo demanda, nunca servidas desde un caché intermedio.
- **Errores de descifrado nunca exponen ciphertext ni clave** — mensaje genérico tanto para formato inválido como para fallo de autenticación GCM (ciphertext manipulado o clave incorrecta).
- **Editar nunca decripta automáticamente** — reemplazar un valor siempre pasa por un input vacío explícito ("Reemplazar SSN"/"Reemplazar número"), nunca un formulario precargado.
- **Excluidos de Búsqueda global y de todo CSV** (Contactos/Pólizas/Comisiones/Reporte de clientes) — ver `docs/SENSITIVE_PII.md`.

### Gestión de la clave de cifrado

- Generación documentada en `.env.example` (comando, nunca una key real de ejemplo funcional).
- **Backup del `PII_ENCRYPTION_KEY` es responsabilidad separada del backup de la base de datos** — un backup de Postgres contiene solo ciphertext; sin la clave correspondiente, esos valores nunca son recuperables. Antes de producción: confirmar que la clave de producción se respalda de forma independiente y segura (gestor de secretos), nunca junto al backup de la base de datos ni en el mismo repositorio/artefacto.
- Rotación de clave / KMS externo: evaluado y diferido explícitamente (ver `docs/SENSITIVE_PII.md`, "Pendiente") — el formato versionado (`v1:...`) permite implementarlo después sin romper datos ya cifrados.
